**结论**：**单个上游 PR 在本机上大多测不出来**；"版本跨度 → 二分定位"能找到足够大的跳变，代码题按这条路线产出。原始数据：`data/code-screen*.jsonl`、`data/span-sweep.jsonl`、`data/bisect-*.jsonl`。

筛选中暴露并已修复的评判者问题：
- 服务端配置 `-np 32 -c 131072` 放不下 16GB，WSL2 让显存溢出到共享内存，吞吐掉到 140 tok/s 且噪声极大 → 筛选配置改为能放下的 `-kvu -c 16384 -fit off`

## 3. 二分定位

**找到**：`740251a920` *cuda : gather batched tensor reads into mapped host memory* (#31391，2026-11-03)。父提交 ~665 → 该提交 ~1290 tok/s（**≈ 1.94×**）。自包含：新增 `ggml-cuda/batch-get.cu`（198 行）+ 分派 6 行 + 测试，共 233 行。

→ 代码题 `code-cuda-batched-reads-c32`（训练集）：base = `71efc559a`，参考 = 该 PR 的 diff。

机理（供复盘，不进题面）：C=32 时每个 decode step 要把 32 个序列的 logits / 采样结果从 GPU 分散读回，原实现逐张量 `cudaMemcpy`，每次都有固定开销；该 PR 把它们收集到一次映射主机内存的读里。这正是 v0 账本上那块"说不出原因"的 `step.gpu_idle`。

prefill 跨度（b9000 → b12242 pp2048 +28.5%）的二分正在进行，目标是一道留出集代码题。

## 4. 代码题的产出方式

```
版本跨度扫描（找大差距）→ 二分定位（找到引入跳变的提交）→ 逐 PR 复测（确认可复现）
  → make_code_task.py（父提交为 base，PR diff 为参考，固定参数）→ calibrate（区分度检查）
```

| 风险 | 处理 |
|---|---|
| 跳变来自多个小提交的累积 | 二分在两半都 < 6% 时停止，报告"分散" |
| 老提交不支持当前 GGUF / 新模型 | 转换器固定在 b12242；老提交加载失败即淘汰 |
| PR 本身编译不过 | 允许"PR + 仅修编译的后续提交" |
| 泄题（Sherpa 能看到上游历史） | Sherpa 的代码题工作区必须截断在 base（M1 runtime 负责） |
