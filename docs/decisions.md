# 决策记录与待定问题

> 配合 [`design.md`](./design.md)（v1）阅读。这里记录：**为什么这样设计**、**哪些已确认**、**哪些还没定**。

## 1. 用户强调的要点（优先级最高）

| # | 要点 | 原话要义 |
|---|---|---|
| E1 | **框架本身要能自迭代** | 不只是知识进化，工具、流程、loop 都要进化；框架要能发现自身的问题 |
| E2 | **确定性门禁 + LLM 决策混合** | 不完全依赖模型能力，在适当的地方加约束保证优化稳定；但不要固定流程 |
| E3 | **防止知识污染** | 担心经验只追加导致上下文膨胀、跨组合冲突、效率低 |
| E4 | **loop 中穿插 LLM 决策** | 并行实验、读中间结果提前叫停等，目的是提高迭代效率 |
| E5 | **与推理框架解耦** | 框架通过 git 引入，优化以 commit 的形式提交到分支上 |
| E6 | **性能很重要** | 性能决定迭代速度；性能敏感的部分用 Rust |
| E7 | **可接入任意 agent** | codebuddy / claude code 等作为可替换的运行时 |
| E8 | **顶层设计完整、易扩展；初版实现可以简单** | |
| E9 | **从第一性原理出发，先顶层后细节；任何设计都可以推翻** | |
| E10 | **当前只用 llama.cpp 打磨 Sherpa** | 代码题也先从 llama.cpp 来；长期大概率会转向自研框架 |

## 2. 已确认的决策

### 2.1 v1 新增（2026-11-10，v0 评审之后）

| # | 决策 | 理由 |
|---|---|---|
| D19 | **核心命题**：Sherpa 的"自身"由 agent 改写，只有在固定的任务基准上证明变强才会保留 | 评审结论，用户认同整体方向 |
| D20 | **权限按"评判者 / 被评判者"划分**，取代 v0 的"代码 / 数据"划分。评判者 = 测量契约、正确性 oracle、Task Bench、记录与溯源、守卫；其余全部可进化，包括代码 | v0 中最有价值的教训都落在了"人改"的代码里，自动进化只覆盖了知识条目 |
| D21 | **结果只能由 kernel 产生**：测量、接受判定、任务得分都在 kernel 里完成，runtime 只是调用方 | 这是 runtime 可以进化的前提 |
| D22 | **外环评判者 = Task Bench**（按任务划分训练集 / 留出集），取代 v0 的 metabench（知识对事实的回放） | v0 的 metabench 在训练集上测试（DES-19）；而且它只能评判知识，评判不了其他资产 |
| D23 | **进化的单位 = 对 sherpa 仓库的 commit**；由复盘 agent 产出；按 T0 / T1 / T2 分层门禁 | 让"流程、工具、代码都能进化"可以落地 |
| D24 | **参考目标来自专家产物，在本机实测**：配置题用专家配置，代码题用专家 PR | 公开基准值大多和我们的硬件对不上（调研结论，见 design 附录 A） |
| D25 | Task Bench 分三类题：配置题、代码题（从框架历史的性能 PR 挖）、陌生题 | 借鉴 GSO / SWE-fficiency |
| D26 | 正确性 oracle：无损动作在目标并发下比对；涉及采样时做分布检验；有损动作用 KL + 任务分数，阈值 99%，生成长度不少于 90%；内置防作弊检测 | 修复 v0 的假阴性（DES-14，以及评审发现的 batch=1 问题），回答 OQ-8、OQ-9 |
| D27 | 测量契约采用现成的开源压测工具并固定版本，走 OpenAI 兼容 API；adapter 不计算指标 | 评审发现 v0 的指标由可进化的 adapter 计算 |
| D28 | 每台机器先跑 llama.cpp 社区标准测试做体检 | 把环境问题和优化空间分开 |
| D29 | 当前阶段只用 llama.cpp；里程碑 M0 → M3（见 design §8） | 用户确认 |
| D30 | 账本降级为"仪器之一"，物理下界、特征、知识解释器都属于被评判者 | 它们都应当可以被证伪、可以进化 |

### 2.2 v0 阶段的决策（标注当前状态）

| # | 决策 | 状态 |

## 3. v0 评审结论（2026-11-10）

评审方式：通读 v0 全部代码和文档，并在本机（5070 Ti + WSL2）上实测环境探测和 codebuddy headless 调用。

| # | 结论 | 证据 |
|---|---|---|
| R1 | v0 证明了内环管线能走通，但没有证明"能力来自框架"和"能自我变强"。走查中开发、规划、分析、执行、提案、审批**都是同一个 IDE agent**；+116% 主要来自 `-np 32`（默认值陷阱） | `retro-v0.md` §1 |
| R2 | 外环缺少任务级评判者，metabench 只能评判知识条目 | `kernel/metabench.py` |
| R3 | 测量逻辑写在可进化的 adapter 里 | `assets/adapters/llama.cpp/adapter.py` 中的 `bench_once`、`parse_trace` |
| R4 | 正确性门禁只验证了 batch=1：greedy 请求是串行发送的，48 个 token 里公共前缀达到 16 就算通过 | `adapter.py` 中的 `greedy`、`kernel/gates.py` |
| R5 | 进化产出的知识大多没人读：`load_priors` 没有调用方，`side_effects` 没人读，`K.query` 不返回 `notes` | `kernel/knowledge.py` |
| R6 | 特征集合写死在代码里，"冲突 → 补变量"的机制没法自主运转 | `model/features.py` |
| R7 | 决策点按方法名分派，brief 在引擎里手工拼接，"loop 可进化"名不副实 | `runtime/engine.py` |
| R8 | 接受判定拿候选和 incumbent **之前存下的**测量结果比较 | `runtime/scheduler.py` 中的 `M.compare(incumbent["measurement"], ...)` |
| R9 | 换到本机就跑不起来：①没有 5070 Ti 的卡规格（`KeyError`）；②`build.sh` 假设 pip 版 CUDA 的目录布局，系统 CUDA 的 CUPTI 在 `extras/CUPTI`，编译失败后被静默吞掉，账本退化为只有一个节点；③codebuddy 的 headless 输出是**消息数组**，`codebuddy.py` 在上面调 `.get` 会崩；④codebuddy 会注入持久化的 auto-memory；⑤`env.py` 写死了 `/root/.workbuddy` 路径 | 本机实测 |
| R10 | 应当保留的设计：理论 vs 实测账本、确定性接受规则、条件写在特征上、派生量重算、资产冻结、handoff 通道、逐项裁决 | |

retro-v0 中 8 个议题的处理：议题 1 → D22（换一个层级来解决）；议题 2、3、5 → 被评判者一侧的改进（议题 3 的 probe 已纳入动作词表）；议题 4、8 → D26、D27；议题 6 → kernel/records 的准则；议题 7 → D20、D23。

## 6. 讨论演进

1. 把问题建模为搜索 → 用户：混合大脑、动作不设边界、框架本身也要进化
2. 两层循环 + 台账 → 用户：台账也是污染
3. 回到第一性原理：按机理组织、沉降为工具、事实 ≠ 结论 → 用户高度认可
4. 机理模型：账本树、物理下界、特征条件
5. 目录 → 用户：框架分仓、Python + Rust、agent 做抽象
6. loop 改为机制与策略分离；进化时机（任务期间冻结）获确认
7. 设计文档 v0 → 另一个 agent 实现 v0，跑通 llama.cpp 全链路（+116%），产出 devlog / retro
8. **独立评审**（用户要求不受已有设计影响）→ 核心命题、评判者/被评判者划分、Task Bench → 用户认同
9. 调研开源 bench → 参考目标来自专家产物、三类题、oracle 方案 → 用户确认只用 llama.cpp 打磨，代码题也从 llama.cpp 来
