# 决策记录与待定问题

> 配合 [`design.md`](./design.md) 阅读。这里记录**为什么这样设计**、**哪些已经确认**、**哪些还没定**。
> 接手的 agent：遇到下面 OQ 列表中的问题，如果它会阻塞当前工作，**先和用户确认，不要自行假设**。

---

## 1. 用户强调的要点（优先级最高）

| # | 要点 | 原话要义 |
|---|---|---|
| E1 | **框架本身要能自迭代** | 不只是知识进化，工具、流程、loop 也要进化；框架要能发现自身的问题 |
| E2 | **确定性门禁 + LLM 决策混合** | 不完全依赖模型能力；在适当的地方加约束，保证优化稳定推进；但不要固定流程 |
| E3 | **防止知识污染** | 担心经验只追加导致上下文膨胀，跨组合产生冲突，效率低 |
| E4 | **loop 中穿插 LLM 决策** | 并行实验、读中间结果提前叫停等，目的是提高迭代效率 |
| E5 | **与推理框架解耦** | 框架通过 git 引入，优化以分支上的 commit 提交 |
| E6 | **性能很重要** | 性能决定迭代速度；性能敏感的部分用 Rust |
| E7 | **可接入任意 agent** | codebuddy / claude code 等作为可替换的运行时 |
| E8 | **顶层设计完整、易扩展，初版实现可以简单** | |
| E9 | **从第一性原理出发，先做顶层思考，再定细节** | |

## 2. 已确认的决策

| # | 决策 | 理由 |
|---|---|---|
| D1 | 大脑采用混合方案：确定性的 harness（测量 / 门禁 / 不变量）+ LLM（诊断 / 决策） | E2 |
| D2 | 动作空间不设边界（调参 → 特性 → 改源码 / 写 kernel） | 用户：只要服务于目标，什么优化都可以做 |
| D3 | 两层循环：内环（任务）+ 外环（Sherpa 自身进化） | E1 |
| D4 | 能进化的东西，由不随之进化的锚点来评判（物理下界 / 真实测量 / 门禁） | 防止 Goodhart |
| D5 | 知识按**机理**组织，不按组合组织；条件写在**特征**上 | 组合无穷，机理有限；冲突 = 缺变量 |
| D6 | 知识持续重构，不追加；成熟的知识沉降为工具 | E3 |
| D7 | 机理模型 = 时间账本树（骨架）+ 物理下界 + 经验 | 用户认可整体思路 |
| D8 | base 版本出厂自带骨架 + 物理，经验为空 | 用户期望 base 版本没有专业知识、越用越强；骨架和物理属于教科书常识（用户未反对） |
| D9 | 推理框架不进 sherpa 仓库；任务运行时通过 git worktree 拉取，优化提交到 `sherpa/<id>` 分支 | E5 |
| D10 | sherpa 内部按框架沉淀 adapter 和框架相关知识（含 codemap） | 用户：主流框架的经验沉淀属于专家知识 |
| D11 | 流程代码用 Python；性能敏感的工具用 Rust | E6 |
| D12 | Agent 执行层做抽象，可接入任意 agent CLI | E7 |
| D13 | 三层结构：策略层（LLM 决策点）/ 机制层（确定性 runtime）/ 执行层（agent backend） | E4 |
| D14 | 决策点 v0 为 plan / monitor / analyze / judge，由事件触发 | E4 |
| D15 | **任务期间资产冻结，不允许进化**；进化只在任务之间进行 | 用户明确确认："不允许在评估的过程中进化" |
| D16 | "够不够好"由 Judge 结合知识来判断，不写死参数；硬性门禁兜底 | 用户：目标函数属于专家知识 |
| D17 | 初期形态是 CLI；运营页面、平台以后再说 | |
| D18 | 顶层接口完整，v0 实现最简（见 design §10） | E8 |

## 4. 待定问题（Open Questions）

### 关于设计

| # | 问题 | 背景与当前倾向 |
|---|---|---|
| **OQ-1** | **事实库的形态与原理** | 用户原话："我也没明白你事实库这个设计的原理，先不着急"。用户担心：只追加的台账会越来越长，本身也成为污染。设计意图是：事实 ≈ 测试用例，知识 ≈ 代码；事实不进上下文，只用于检验知识和离线评测（用户认为"可以用于离线评测"这一点有道理）。**下一步需要专门讨论**：存什么、存多久、如何压缩或淘汰、和 metabench 怎么配合 |
| OQ-2 | v0 用哪个框架 | vLLM 是主战场，但在 sm_120 + WSL2 上安装风险高；llama.cpp 最容易跑通，也适合验证框架无关性。倾向：v0 用 llama.cpp 跑通闭环，v1 上 vLLM |
| OQ-3 | v0 的目标开发机 | 本机是 5070 Ti + WSL2，另有一台 4090 开发机（用户说日常开发用它）。4090 机器是不是原生 Linux？profile 能力是否完整？ |
| OQ-4 | 每次 LLM 调用是否都开新会话 | 倾向：每次决策或子任务都开新会话，由 Sherpa 生成状态简报传入，避免上下文膨胀，也便于更换 backend。代价是交接必须结构化。用户未回应 |
| OQ-5 | 执行层子任务的粒度 | 例如"实验"这一步（改代码 + 编译 + 起服务 + bench）是交给一个 agent 一次做完，还是拆细？会影响 backend 接口设计。用户未回应 |
| OQ-6 | 自修改的合入权 | 见 P1 |
| OQ-7 | 资产与框架代码是否分仓 | 提议：sherpa 仓库自带 base 资产，团队资产作为 overlay 叠加（便于共享 base、团队私有积累、多套资产包）。用户回应的是"推理框架要分仓"（已成为 D9），资产的 overlay 方案尚未讨论 |
| OQ-8 | 硬性门禁的具体形式 | 用户："可以给出一些硬性的门禁，这是具体实现问题，后面讨论" |
| OQ-9 | 正确性门禁如何处理有损动作 | greedy 输出逐 token 对比只适用于无损优化；量化等需要 eval 集加容差。用哪个 eval、容差多少？ |
| OQ-10 | 负载从哪里来 | 输入输出长度分布、并发等。尚未讨论；`model/specs/workload` 需要定义来源（合成 / 数据集 / 线上采样） |
| OQ-11 | 知识冷启动 | 用户：可以让 agent 从团队的 vLLM 优化，以及开源 vLLM / SGLang / llama.cpp 的经验中抽取。抽取出来的形态需要与 design §4.4 对齐。时机待定 |
| OQ-12 | metabench 的具体设计 | 离线回放（基于事实集，成本低）+ 在线任务集（真机，成本高）。任务集如何构建，指标如何汇总？ |
| OQ-13 | backend 抽象接口定义 | 输入：指令 / 上下文 / 允许的工具 / 工作目录 / 输出 schema / 预算；输出：结构化结果。v0 接 codebuddy CLI 的 headless 模式（**参数需要实测确认**） |
| OQ-14 | agent 执行代码的安全边界 | 尚未讨论：agent 在开发机上改代码、跑命令时的沙箱 / 权限范围 |
| OQ-15 | 非 GPU 场景（llama.cpp CPU / 混合推理）下物理模型如何覆盖 | 账本树和下界计算需要支持 CPU 内存带宽、算力 |
| OQ-16 | 决策点的模型分档 | strong / fast 具体用哪些模型，如何配置 |

## 6. 讨论演进（便于理解设计是怎么来的）

1. 搜索问题建模 → 用户：大脑用混合方案，动作不设边界，自迭代的范围要更宽（框架本身也要进化）
2. 两层循环 + kernel / assets / brain，加上"只追加台账"的想法 → 用户：台账也是污染（越来越长、冲突、效率低）
3. 回到第一性原理：专家知识的形态 → 按机理组织、沉降为工具、事实 ≠ 结论 → 用户高度认可
4. 机理模型：时间账本树、物理下界、特征条件 → 用户认可，但觉得太抽象，要求落到目录
5. 目录 v1 → 用户：框架分仓、Python + Rust、agent 做抽象，loop 需要专门设计
6. 两层 loop（固定流程 + backend）→ 用户：loop 中要穿插 LLM 决策 → 改为机制与策略分离的三层结构
7. 进化时机（任务期间冻结）获确认；环境与"顶层完整、v0 从简"原则确定
