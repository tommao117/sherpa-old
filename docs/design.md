> 决策记录与待定问题：[`decisions.md`](./decisions.md)。

## 0. 定位

Sherpa（夏尔巴人，领路人）是一个**自迭代的推理优化框架**。它**不做推理**，而是去优化已有的推理框架。

```
输入：模型 × 卡型/环境 × 推理框架@版本      例：Qwen3-0.6B × RTX 4090 × vllm@v0.x
  │
  ▼  Sherpa
部署 → bench → profile → 诊断 → 优化 → 验证 → …… → 交付部署
  │
  ▼
输出：① 优化后的可部署产物（框架分支 + commit + 启动命令）
      ② Sherpa 自身变强（知识 / 工具 / 流程得到更新）
```

| 特性 | 说明 |
|---|---|
| 框架无关 | 支持 vLLM / SGLang / llama.cpp，以及**长期主力：自研推理框架** |
| 动作无边界 | 从调参、开关特性，到改框架源码、写 kernel，只要服务于目标都可以做 |
| 自迭代 | base 版本没有专业知识，越用越强。知识、工具、**流程本身**都会进化 |
| 形态 | 初期是 CLI，后续增加运营页面，再往后做成平台 |

## 1. 第一性原理

### 1.1 推理优化是带约束的搜索

```
给定  Context = (模型, 卡型/拓扑, 框架+版本, 负载, 目标)
寻找  Action  = 配置 / 特性 / 代码改动
使得  目标最优（吞吐、TTFT、TPOT、成本……）
约束  精度不掉、稳定、可复现、可交付
```

### 1.2 专家为什么越做越快

```
解决时间 ≈ 实验次数 × 单次实验成本
             │            └─ 靠【工具】降低：自动化、可复用、跑得快
             └─ 靠【判断】降低：方向选得准，知道上限在哪、何时该停
```

专家积累的不是"组合 A 上开 X 有效"这类条目（组合有无穷多），而是：

| 形态 | 例子 | 泛化性 | 是否占上下文 |
|---|---|---|---|
| 机理认知 | 小 batch decode 是访存瓶颈，下界 = 权重字节数 / 带宽 | 极强 | 少 |
| 诊断套路 | 先看 GPU 空闲率 → kernel 分布 → 通信 | 强 | 少 |
| 工具 | 自动算 roofline、标出瓶颈的脚本 | 强，且确定 | **不占** |
| 个案记忆 | "上次 Qwen3 在 H20 上……" | 弱，只能类比 | 按需取 |

### 1.3 Sherpa 只需要四样东西

```
              ┌──────────── 锚点（不随 Sherpa 进化）────────────┐
              │  物理：理论下界   事实：真实测量   门禁：正确性     │
              └──────────────────────┬────────────────────────┘
                                     │ 校准
       ┌─────────────────────────────┼──────────────────────────┐
       │  认知（机理模型）  ◄── 成长 ──►  手脚（工具 / 适配器）     │
       │  判断方向、上限、何时停     ▲     感知（bench/profile）、行动 │
       │                          │                             │
       │                    经历（一次次任务）                      │
       └──────────────────────────┬──────────────────────────────┘
                                  │ 推理
                              大脑（LLM，外部提供，更强的模型自动受益）
```

**核心原则：能进化的东西，必须由不随它一起进化的东西来评判。** 否则系统会学会降低标准，宣布"够好了"（Goodhart 效应）。

## 2. 两层循环

```
┌─ 外环：Sherpa 自身进化（让"专家"变强）─────────────── 只在任务之间发生 ─┐
│  评判者：Metabench（离线回放事实集 + 在线任务集）                       │
│                                                                    │
│   ┌─ 内环：一次优化任务（让 模型×卡×框架 变快）────────────────┐       │
│   │  评判者：物理测量（bench + 门禁）                          │       │
│   │  资产在任务期间【冻结】                                     │       │
│   └──────────────────────┬──────────────────────────────────┘       │
│                          │ 事实                                     │
│                          ▼                                          │
│     evolve：资产变更提案 → metabench 评测 → 合入 / 回滚               │
└────────────────────────────────────────────────────────────────────┘
```

**进化时机（已确认）**：任务进行中不允许进化，loop 不能改写自己；进化只在任务之间由 `evolve` 统一进行。否则任务结果无法归因，也无法评估。

## 3. 机理模型（认知的骨架）

### 3.1 时间账本树

```
请求级   SLO 下的吞吐 / TTFT / TPOT
  └ 调度     batch 组成、排队、prefill/decode 混排、KV 容量对并发的限制
步级     一次 forward（prefill / decode）
  ├ GPU 忙
  └ GPU 闲   CPU 调度、Python overhead、kernel launch、同步
算子级   Attention / GEMM / MoE / 通信 / 采样 ……
核级     kernel：实测 vs max(FLOPs / 峰值算力, 字节 / 峰值带宽)
```

每个节点有三列：

| 理论下界（物理算出） | 实测（profile） | 差距 = 优化空间 |
|---|---|---|

> 示例（示意数字）：Qwen3-0.6B，H20，decode，bs=1。权重约 1.2GB，带宽约 4TB/s，每步下界约 0.3ms。如果实测 4ms，说明 GPU 大部分时间在空闲，瓶颈在 CPU/launch，方向应该是 cuda graph、减少 Python 开销，而不是换 attention kernel。

### 3.2 两类优化动作

```
 实测 ───────┐
             │ ① 缩小差距（close_gap）：cuda graph、kernel 调优、overlap
 理论下界 ────┤
             │ ② 移动下界（move_bound）：改变工作量本身
 更低下界 ────┘   量化、投机解码、并行策略、更大 batch、PD 分离
```

每个动作都挂在账本的某个节点上，并标明类型和作用项（FLOPs / 字节 / 空闲时间）。

### 3.3 条件写在特征上，不写组合名

| | 峰值算力（约） | 带宽（约） | 拐点 = 算力 / 带宽 |
|---|---|---|---|
| H20 | 148 TFLOPS | 4.0 TB/s | **~37** |
| H100 | 989 TFLOPS | 3.35 TB/s | **~295** |

算术强度为 100 的算子，在 H20 上是算力瓶颈，在 H100 上是访存瓶颈。同一个动作效果相反，这是物理规律，不是知识冲突。

→ 条件写成 `when: { 拐点 < 算术强度, gpu_idle_ratio < 0.1 }`，而不是 `H20 + vLLM`。遇到新组合时先投影到特征空间，已有经验就能迁移。

### 3.4 组成与用途

| 部分 | 内容 | 形态 | 是否进化 |
|---|---|---|---|
| 骨架 | 账本树 | 数据结构 | 很少变，出现新算子（MLA、线性注意力……）时加节点 |
| 物理 | 由模型 + 卡 + 负载算出各节点下界 | 确定性代码 | 基本不变 |
| 经验 | ① 效率先验（"X 卡上 GEMM 能达到峰值的 N%"）<br>② 动作目录（节点 + 特征条件 + 预期收益） | 结构化条目，成熟后沉降为工具 | **持续进化** |

**base 版本 = 骨架 + 物理（教科书常识，出厂自带）+ 空的经验。**

| 用途 | 做法 |
|---|---|
| 诊断 | 实测账本对比理论账本，按"差距 × 时间占比"排序 |
| 指导 | 在节点上查动作目录，按特征条件过滤，按预期收益排序 |
| 判断够好 | 所有差距要么低于效率先验，要么已被已知的不可消除因素解释 |

### 3.5 局限

- 账本只覆盖**时间**维度。**容量**（显存会限制并发）和**精度**（量化等）需要作为额外的约束维度
- kernel 到算子的映射依赖具体框架，由 adapter 负责

## 4. 知识：组织、成熟与冲突

### 4.1 成熟梯度

```
个案 ──归纳──► 机理 / 规则 ──固化──► 工具 / 代码
(多、弱、散)      (少、强)          (确定、零上下文成本)
```

"工具越来越智能"，就是知识从文本流向代码的过程。决策点和 loop 步骤同样遵循这条梯度：LLM 决策 → 规则。

### 4.2 冲突是信号，不是污染

```
旧：开 X 能提速
冲突：A 有效，B 无效      → 结论漏了一个变量
修正：X 只在【瓶颈 = 访存】时有效；B 的瓶颈是通信
```

知识库像代码库一样**持续重构**，而不是追加。目标是越用越小、越用越准。

### 4.3 事实 vs 结论

| | 事实 | 结论（知识） |
|---|---|---|
| 例 | exp#1023：组合 A，开 X，TPOT -18% | 访存瓶颈下 X 有效 |
| 会冲突吗 | 不会，只是观测 | 会 |
| 维护 | 只存，**不进上下文** | 持续重构 |
| 作用 | 检验知识（≈ 测试用例） | 指导行动（≈ 代码） |

知识重构之后，要能解释历史事实，至少不能比之前更差，这就是离线评测。

> 用户对事实库的形态和原理**尚未认同**（担心无限增长、成为新的污染）。见 `decisions.md` 中的 OQ-1。

### 4.4 一条经验的示例

```yaml
# assets/knowledge/actions/cuda-graph.yaml
id: cuda-graph
node: step.gpu_idle
kind: close_gap
when: { phase: decode, gpu_idle_ratio: ">0.3" }
effect: { gpu_idle_ratio: "-60% ~ -90%" }
evidence: [f-0012, f-0031]
counter: []
apply:
  vllm: "去掉 --enforce-eager"
```

### 4.5 学习由"意外"驱动

| 信号 | 含义 | 处理 |
|---|---|---|
| 预测误差 | 预估 -18%，实测 -2% | 条件缺变量 → 修正条件 |
| 账对不平 | 时间去向解释不了 | 骨架缺节点，或物理模型不准 |
| 重复劳动 | 同一手工操作重复 N 次 | 沉降为工具 |
| 决策复盘 | Monitor 叫停是否正确 | 修正 policy |

### 4.6 Sherpa 进化的度量

| 指标 | 怎么测 | 代表什么 |
|---|---|---|
| 预测误差 ↓ | 在事实集上离线回放 | 判断更准 |
| 实验次数 ↓ | 真实任务统计 | 方向更准 |
| 离理论下界的距离 ↓ | 任务结束时的账本 | 优化更彻底 |

## 5. Agent Loop：机制与策略分离

LLM 不只是执行子任务的工人，它还参与 loop 的**控制流**：并行开几路实验、盯中间结果、提前叫停。

```
┌─ 策略层（LLM 决策点，可进化）──────────────────────────────────┐
│   Planner   开哪些实验？并行几路？分配什么资源？                  │
│   Monitor   中间结果不对？继续 / 叫停 / 调整                     │
│   Analyst   这次实验说明了什么？和预测差在哪里？                   │
│   Judge     整体够好了吗？要不要换大方向？                        │
└───────────────────────▲───────────────┬──────────────────────┘
               事件触发   │               │ 结构化决策
┌─ 机制层（Runtime，确定性）──────────────┴──────────────────────┐
│  资源池   实验生命周期   事件总线   状态存储   不变量检查            │
└──────────────────────────┬────────────────────────────────────┘
                           │ 具体干活
┌─ 执行层（Agent Backend，可替换）──────────────────────────────┐
│  改代码、编译、排错……  codebuddy CLI / claude code / codex / 自研 │
└──────────────────────────────────────────────────────────────┘
```

### 5.1 时间线示例

```
Planner  有 2 张空卡 → 并行开 E1(cuda graph)、E2(fp8 kv)
GPU0  E1: 编译─起服务─bench ▓▓▓▓▓▓▓▓ 完成 → Analyst: TPOT -40%，符合预测
GPU1  E2: 编译─起服务─bench ▓▓▓
          Watcher(规则): 吞吐比 baseline 低 30% → 上报
          Monitor(LLM): 读日志发现走了慢路径 → 叫停，记事实
Planner  结合 E1 的成功和 E2 的失败原因 → 开 E3 ……
```

### 5.2 设计要点

1. **分级上报**：指标流 → Watcher（规则/异常检测）→ 快模型 → 强模型。只有当决策可能省下的 GPU 时间大于调用代价时，才调用 LLM
2. **决策点可以沉降**：同一个决策点可以由规则、LLM、或"规则兜底 + LLM"承担
3. **决策可被评估**：每个决策都记录理由和当时的输入，便于事后复盘
4. **状态存在 Sherpa 里，不在 agent 上下文里**：每次调用 LLM 时，由 Sherpa 生成精简的状态简报传入（倾向如此，见 OQ-4）
5. **并行实验隔离**：独占 GPU，独立 worktree/分支，只有相同环境下的测量结果才能互相比较

### 5.3 决策点配置

```yaml
# assets/policies/hooks.yaml
decisions:
  plan:
    on: [task_start, slot_freed, experiment_concluded]
    policy: plan.md
    model: strong
    output: schema/plan.json        # 开哪些实验、分配哪些资源、预测收益
  monitor:
    on: [watcher_alert]
    policy: monitor.md
    model: fast
    output: { action: continue | kill | adjust, reason }
  analyze:
    on: [experiment_finished, experiment_killed]
    policy: analyze.md
  judge:
    on: [experiment_concluded]
    policy: judge.md
```

**可进化的 loop** 包括：决策点集合、各自的 policy、触发条件、由规则还是 LLM 承担。Runtime 原语和不变量保持不变。

### 5.4 不变量（`kernel/invariants`，任何 policy 都不能绕过）

- 接受任何改动之前，必须经过测量和门禁
- 实验开始之前必须声明预测收益（用于计算预测误差）
- 每个实验无论成功、失败还是被叫停，都要产出事实
- 不超出预算上限
- 并行实验之间相互隔离
- 任务期间资产冻结

### 5.5 门禁（`kernel/gates`）

动作没有边界，所以门禁就是唯一的边界：

| 门禁 | 含义 |
|---|---|
| 正确性 | 输出与参考一致 / eval 不掉（量化等有损动作需要容差，见 OQ-9） |
| 可复现 | 多次测量的方差在阈值内 |
| 可交付 | 产物能在干净环境中独立部署 |

"够不够好"由 Judge 结合知识来判断（不是一个写死的参数），硬性门禁兜底（具体形式见 OQ-8）。

## 6. 与推理框架解耦

```
sherpa 仓库：只放"关于框架的知识"
  assets/adapters/vllm/
    ├── adapter.yaml   # 仓库地址、支持的版本、安装方式
    ├── deploy.py      # 起服务 / 健康检查 / 停服务
    ├── bench.py       # 输出成 kernel/measure 规定的格式
    ├── profile.py     # 采集 trace，把 kernel 映射到账本节点
    ├── knobs.yaml     # 可调参数，以及作用在账本的哪个节点
    └── codemap.md     # 源码地图（做代码级优化时需要）

任务运行时才拉取框架源码（git）
  sherpa-data/tasks/<id>/framework/      ← worktree: vllm@<tag>
     └── 分支 sherpa/<id>               ← 优化以 commit 形式提交
  交付物 = 分支 + commit hash + 启动命令
```

自研框架也走同一套机制。

## 7. 目录结构

**目录即权限边界。**

```
sherpa/
├── kernel/                 # 锚点（只能人改）
│   ├── facts/              #   事实的 schema / 写入 / 查询
│   ├── measure/            #   测量契约：结果格式、重复次数、方差检验
│   ├── gates/              #   正确性 / 可复现 / 可交付
│   ├── invariants/         #   §5.4 不变量
│   ├── evolve/             #   资产变更：提案 → 评测 → 合入 / 回滚
│   └── metabench/          #   外环评测
├── model/                  # 机理模型：骨架 + 物理
│   ├── ledger/             #   账本树节点定义
│   ├── physics/            #   各类算子的 FLOPs / 字节 → 下界
│   ├── specs/              #   hw/ 卡规格、arch/ 模型结构、workload/ 负载
│   └── features/           #   (模型, 卡, 负载) → 特征空间
├── assets/                 # 可进化资产
│   ├── adapters/<fw>/      #   框架适配器（§6）
│   ├── knowledge/          #   priors/ 效率先验、actions/ 动作目录
│   ├── tools/              #   由经验沉降出来的工具
│   ├── playbooks/          #   执行层：某类子任务怎么做（改代码、接入新框架……）
│   └── policies/           #   策略层：决策点 policy + hooks.yaml
├── runtime/                # 机制层
│   ├── engine/             #   事件循环：把事件路由到决策点，执行决策，检查不变量
│   ├── scheduler/          #   资源池、实验生命周期、并行与隔离
│   ├── events/             #   事件总线
│   ├── watchers/           #   确定性监控，决定哪些事件上报给 LLM
│   ├── backends/           #   agent 执行层抽象
│   ├── workspace/          #   拉取框架、建 worktree 和分支
│   └── env/                #   执行环境：本地 / SSH / 云
├── crates/                 # Rust：压测客户端、trace 解析、账本计算
├── cli/                    # sherpa 命令
├── docs/
└── tests/

sherpa-data/                # 运行时数据，不进代码仓
├── facts/
├── tasks/<task-id>/
│   ├── context.yaml        #   模型 / 卡 / 框架+版本 / 负载 / 目标
│   ├── framework/          #   框架 worktree
│   ├── ledger/             #   每一轮的理论账本 vs 实测账本
│   ├── experiments/        #   假设 → 预测 → 改动 → 结果 → 结论
│   ├── decisions/          #   每个决策的输入 / 输出 / 理由
│   ├── report.md
│   └── deliverable/
└── artifacts/              # 原始 trace、大文件
```

### 7.1 权限分级（默认方案，见 OQ-6）

| 目录 | 谁改 | 合入方式 |
|---|---|---|
| `kernel/` `runtime/` `cli/` `crates/` | 人 | 正常 PR |
| `model/` | Sherpa 提案，人审 | |
| `assets/knowledge/` | Sherpa | 离线回放不退化即自动合入 |
| `assets/tools/` `playbooks/` `policies/` `adapters/` | Sherpa 提案 | 初期人审，逐步放开 |

### 7.2 语言分工

| Rust（`crates/`） | Python |
|---|---|
| 压测客户端（高并发下 Python 客户端会让**测量失真**） | 流程编排、runtime |
| trace 解析（GB 级） | adapter |
| 账本计算、特征投影 | agent 新写的工具（成为热点后再用 Rust 重写） |

### 7.3 CLI 雏形

| 命令 | 作用 |
|---|---|
| `sherpa run` | 完整优化任务 |
| `sherpa deploy` / `bench` / `profile` | 单独执行某一步 |
| `sherpa ledger` | 理论账本 vs 实测账本 |
| `sherpa facts` | 查询事实 |
| `sherpa evolve` | 查看、审批资产变更提案 |
| `sherpa metabench` | 评测 Sherpa 自身 |

## 8. 一次任务的完整流程

```
sherpa run --model Qwen/Qwen3-0.6B --hw local --framework vllm@<tag>

 ① model/specs + features     解析输入 → 特征
 ② model/physics              理论账本
 ③ runtime/workspace          拉框架 worktree，建分支 sherpa/<id>
 ④ adapters/<fw>              部署 → bench → profile → 实测账本
 ⑤ kernel/measure             校验测量是否可信
 ┌──────────────── 事件驱动 ────────────────┐
 │ Planner 出实验计划（带预测）→ scheduler 分配资源    │
 │ 执行层施加改动 → bench ⇢ Watcher / Monitor 盯着    │
 │ gates → Analyst → facts                           │
 │ Judge：继续 / 换方向 / 结束                         │
 └──────────────────────────────────────────┘
 ⑥ adapters/deploy            交付物
 ⑦ kernel/evolve              基于本次事实产出资产变更提案（任务结束后）
```

## 9. 演进路线

```
P0 内核 + 最小闭环：kernel(measure/gates/facts) + 1 个 adapter，端到端跑通
P1 内环：策略层四个决策点工作，事件驱动
P2 沉淀：事实 → 经验 → 按特征检索注入
P3 外环：metabench + evolve
P4 泛化：更多框架 / 自研框架 / 多卡 / 云
```

## 10. v0 范围：顶层设计完整，实现从简

**原则：接口按完整设计来定，实现用最简单的。扩展时替换实现，不改接口。**

| 组件 | 完整设计 | v0 实现 |
|---|---|---|
| scheduler | 本地 / SSH / 云资源池，并行，隔离 | 本地单卡，并发 = 1（仍然走接口） |
| events | 事件总线 | 进程内队列 |
| watchers | 规则 + 异常检测（Rust） | 几条阈值规则（Python） |
| backends | 可接入任意 agent | 只接 codebuddy CLI，接口先定义好 |
| policies | 四个决策点 + 模型分档 | 四个决策点都有，用同一个模型；monitor 只处理崩溃和明显劣化 |
| physics | 各类算子 | dense decoder（Qwen3 类）+ 本地卡规格 |
| adapters | 多个框架 | 1 个（vLLM 还是 llama.cpp，见 OQ-2） |
| measure | Rust 压测 + 方差检验 | 包装框架自带的 bench，输出统一格式 |
| gates | 三类门禁 | 正确性：greedy 输出与 baseline 逐 token 对比；可复现：重复 3 次 |
| facts | 待定（OQ-1） | 每个任务一个 JSONL，schema 带版本号 |
| evolve | 提案 → metabench → 合入 | 只产出提案文件，由人审 |
| metabench | 离线 + 在线 | 只留接口 |
| crates | 三个组件 | 只留目录 |

**v0 验收标准**：`sherpa run` 能端到端跑通一次（拉框架 → 部署 → baseline → profile → 账本 → 至少一轮实验 → 门禁 → 记事实 → 交付 → 提案），每一步的产物都落在 §7 规定的位置。不要求优化效果。
